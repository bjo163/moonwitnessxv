# M39 — ECHOLOG storage and attachments

**Purpose:** build `apps/echolog` as a bounded, **stateless** storage service owning domain **D19 Object Storage & Attachments** — immutable content-addressed objects and JSON sidecar metadata on its own filesystem volume, REST object API, and the owner-amended limited S3-compatible server endpoint. MinIO is not used or required. **This is a milestone context file, not a status tracker.** Canonical source: [TODO](../../TODO.md). Decision: [ADR-0007](../decisions/ADR-0007-echolog-storage.md). Contract: [ECHOLOG](../architecture/ECHOLOG.md).

**Gate order is deliberate:** M39-01..M39-05 upgrade the documents and the register **before** any code. Because ECHOLOG owns **no tables**, a task that quietly imports `drizzle-orm` or `postgres` is out of scope, not merely early: it would break the closed SQL-owner set that ADR-0006 established.

**Exit gate:** upload → metadata → download → delete proven on both drivers; bytes never stored in Postgres; retention and legal hold refuse premature deletion; no consumer holds driver credentials; stopping the service leaves every object intact.

**Rollback:** stop the service. Objects stay untouched because nothing else writes them, and there is no schema to revert.

**Hard sequencing:** 01 → 05 (documents) → **06 → 07** → 08 → 12 (code).

**Order rule learned from M38:** the app skeleton (M39-06) comes **before** the port/runner/env wiring (M39-07). `scripts/dev.mjs` must not name a package that does not exist, and `.env.example` must not declare a variable no code reads — `env-contract.test.ts` rejects both.

**Related gate:** the owner-deferred off-host backup task may use ECHOLOG only when ECHOLOG runs on a host separate from the backup source and a restore is demonstrated. M39-10 implements and tests the S3-compatible protocol; it does not by itself prove off-host durability or close M04-05.
