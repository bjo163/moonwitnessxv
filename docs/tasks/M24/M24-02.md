# M24-02 — World observation provenance and measurement contract

**Status: specification proposal; no provider or rights approval.** This leaf defines the metadata contract needed before any sourced observation can be accepted. ## Scope and observed baseline

The single owner for operational source configuration and captured monitor signals remains ARSY/MoonQL Monitor; Sentinel is a worker and Dock/Headquarters are projections. This document creates no domain, table, route, provider registry, identity authority, or second data owner. See [Blueprint D10](../../../BLUEPRINT.md), [ADR-0001](../../decisions/ADR-0001-arsy-is-xv-hub.md), and [ADR-0002](../../decisions/ADR-0002-additive-moonql-domains.md).

The current `apps/sentinel/src/types.ts` `CapturedSignalInput` has only optional `publishedAt` and no measurement unit, observed time, location precision, source edition, or revision. `apps/sentinel/src/index.ts` substitutes the current time for missing `publishedAt`; it also defaults missing counts and sentiment. Therefore the present shape cannot establish a sourced physical observation. Existing signal/news capture is distinct from a validated D10 measurement.

## Proposed record contract

Every **accepted D10 observation** must be attributable to all of the following, or remain unaccepted (`UNKNOWN`/quarantined) and unavailable to factual public projections:

| Field | Requirement |
| --- | --- |
| `observationId` | Stable XV identifier for this logical observation; never derived from a title or approximate location. |
| `providerRef` | Opaque reference to an authorized provider/source record owned by the existing source authority; accompanied by `providerRecordId` or a stable source locator when supplied. A provider name alone is insufficient. |
| `sourceEdition` | Optional provider dataset/API edition or schema version, only when actually supplied or pinned. Never invent one. |
| `observedAt` | Time the provider says the event/measurement was observed, RFC 3339 with explicit offset or UTC. Required for an accepted time-specific observation. Preserve provider precision; do not substitute publish or ingest time. |
| `publishedAt` | Provider publication time, nullable and separate from observation time. Missing stays null. |
| `ingestedAt` | Server-assigned time XV received the record; not represented as event/measurement time. |
| `revision` | Provider revision/version/sequence when available, plus `supersedesObservationId` for an explicit correction. If provider supplies no revision, record absence; never silently overwrite history. |
| `observedValue` | Numeric or categorical provider value with the provider's original representation retained where practical; null/missing is not zero. |
| `unit` | Machine-readable UCUM unit for quantitative values, plus original provider unit and an explicit conversion record if normalized. No unit conversion without a defined transform and test. Non-quantitative events use a declared value type, not a fabricated unit. |
| `location` | Optional coordinate/region reference plus `geoPrecision` (`EXACT`, `APPROXIMATE`, `ADMIN_AREA`, `REGION`, `UNKNOWN`) and CRS when coordinates exist. Preserve provider precision and reduce it where privacy/safety requires; never imply a precise point from a named region. |
| `uncertainty` | Provider uncertainty/quality flag and its meaning when available. Do not translate missing quality into “verified” or a confidence score. |
| `rightsSnapshotRef` | Reference to the applicable source authorization/rights decision. Missing, expired, disputed, or unknown rights means no collection/public release; this contract does not grant rights. |
| `epistemicClass` | Explicitly distinguish `PROVIDER_OBSERVATION`, `NEWS_OR_SOCIAL_SIGNAL`, `SIMULATION`, and `XV_DERIVED`. Only the first may represent a provider measurement, subject to provenance and rights gates. |

Fields are conceptual names, not a schema migration commitment. Exact wire/storage names and validation belong to a separately scoped implementation after prerequisite egress and rights gates.

## Time, units, location and revisions

- Keep `observedAt`, `publishedAt`, `ingestedAt`, and any event `occurredAt` as distinct nullable slots. Never fill one from another. If an accepted observation needs a time but only publication time exists, reject it as a measurement or classify it accurately as a publication/event signal.
- Preserve original numeric value/unit and source precision. A normalized value is derived data and must include conversion method/version and source value; rounding must not imply more precision than the source.
- Location is optional. Store the coarsest precision needed for the use case, use a CRS identifier with coordinates, and suppress coordinates for sensitive or rights-restricted sources. Do not geolocate people or infer exact locations from text as part of this contract.
- Corrections append a new revision linked to the prior one. Public projections identify the current revision and correction state while keeping an auditable chain under existing retention/access policy. Replays with the same source locator and revision must be idempotent; conflicting payloads for that key are a conflict, not last-write-wins.
- “Freshness” is a policy computed from source-specific cadence and `observedAt`; it is not proof of accuracy. Without a policy or parseable timestamp, freshness is `UNKNOWN`, never “live”.

## Validation and exposure rules

1. Reject or quarantine an observation missing provider attribution, a parseable required `observedAt`, a valid value/type, or a quantitative unit. Keep `publishedAt` nullable; do not default missing values/counts to zero for a D10 observation.
2. The full production contract must reject malformed timestamps, unsupported units, non-finite numeric values, invalid coordinate ranges/CRS, impossible precision claims, and revision conflicts. Preserve a bounded reason code; do not expose raw provider payloads or credentials in errors/logs. The current test-only validator checks only timestamp syntax, finite values, coordinate ranges/CRS presence, and required nonempty units; unit vocabulary, precision consistency, and cross-record revision conflict checks remain future implementation work.
3. Do not infer a measurement from a news/social signal, simulation, AI summary, seeded fixture, or a source label. UI must show epistemic class, source, observation time, and stale/unknown state; no `verified`, `live`, or green health claim follows from structural validation alone.
4. A structurally valid record is not necessarily true, licensed, safe to publish, or human-reviewed. Existing source rights, privacy, security, and D08 release gates remain authoritative; this proposal does not replace them.

## Acceptance evidence for this specification leaf

- Positive contract case: an observation with provider reference, explicit observed time, value/unit, declared geo precision, and revision/provenance fields is structurally representable without conflating timestamps.
- Negative cases: missing provider or required observed time, missing quantitative unit, malformed publication/observation timestamp, non-finite value, and invalid/mismatched coordinates are rejected. Null publication time and absent optional location remain valid when the observation otherwise meets its contract. A validator cannot determine whether a caller semantically copied a publication time into `observedAt`; provenance review and provider-specific parsing must establish that distinction.
- Executable contract cases are in `apps/sentinel/test/observation-contract.test.ts` and the test-only validator is in `apps/sentinel/test/observation-contract.ts`; the Sentinel package test script includes them. They verify the proposed shape only; production ingest does not call this validator.
