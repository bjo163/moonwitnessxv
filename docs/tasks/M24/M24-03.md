# M24-03 — Design controlled outbound egress, quotas, retry and caching

**Status: provider-neutral design contract; production egress stays disabled.** This leaf specifies the controls required before future live adapters. TODO.md remains the sole status register. It selects no provider and authorizes no fetch or alert.

## Scope and observed baseline

The ARSY/MoonQL Monitor remains source/task owner; Sentinel is a worker. M03-07's SSRF mitigation covers ARSY/Radio and does not prove Sentinel safety. Current Sentinel has separate outbound paths for source drivers, AI Gateway `agent`, and Discord/Telegram webhooks. `EGRESS_ENABLED` does not guard `agent`; source and worker endpoint URLs are passed to `fetch` without common destination policy. Webhook POST has no shared quota, deduplication, or review gate. RSS may use current time when source time is missing, so cache/freshness must not present that fallback as provider event time.

See the full provider-neutral contract at [M24-03 controlled egress design](../../design/M24-03-controlled-egress.md). It defines capability classes, default-deny, URL/DNS/redirect policy, budgets, bounded retries, circuit-break behavior, cache limits, alert suppression and log redaction.

## Executable design evidence

The pure test-only policy model and cases are `apps/sentinel/test/egress-policy-contract.ts` and `apps/sentinel/test/egress-policy-contract.test.ts`. They open no sockets and are not imported by production. Positive cases cover an explicitly authorized provider GET, a fixed internal-service origin, and a single approved alert. Negative cases cover disabled flags, unknown class, uncleared rights, unapproved origin, credentials/fragment, redirect, unsafe resolved address, wrong provider method, exhausted budget, fallback provider, duplicate alert, alert retry, and malformed URL.

The model is policy evidence, not runtime enforcement. M24-04 must apply a real, vetted SSRF guard to every production fetch path and prove denied requests do not call `fetch`; all live flags stay off until then. No provider terms, source rights or external endpoint are approved by this task.

## Acceptance and limitations

- Positive: policy model permits a rights-cleared allowlisted read-only request with a public address and available quota; internal calls require an exact configured origin/path; a separate alert capability permits one approved notification.
- Negative: the cases listed above return stable denial codes or suppress dispatch without network access.
- No production outbound code, provider cache, alert routing or network integration changes in this leaf. Runtime enforcement, DNS rebinding resistance, full IPv4/IPv6 special-range coverage, quota accounting, retry timing, cache correctness, and fetch-spy evidence remain M24-04 implementation requirements.
- AI technical review does not grant legal/privacy approval or source rights. The existing source rights and D08 release authorities remain unchanged.
