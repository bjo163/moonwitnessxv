# M38-10 — Add the Telegram provider, webhook verification and provider-security contract

**EXECUTABLE LEAF, NOT VERIFIED** · Priority P1 · Difficulty D3. [Canonical task state](../../../TODO.md) · [Milestone](../../milestones/M38.md).

## Objective and grounded context
One adapter is not an abstraction. Telegram's official Bot API is the cheapest second proof and carries no ToS exposure. Because `apps/**` may not import `node:crypto`, signature/secret verification must live in a package.

## Boundaries
- Paths: `packages/skylink-telegram/*`, `packages/skylink-core/src/verify.ts`, `docs/architecture/SECURITY.md`.
- grammY pinned; no token in source, logs or the database.
- Webhook routes reject unsigned/incorrectly-signed payloads before parsing.
- `docs/architecture/SECURITY.md` must record credential handling and `messages.raw` retention/PII.

## Work plan
1. Pin the SHA; read the WhatsApp adapter contract and the security doc.
2. Implement the Telegram adapter against the same provider contract (normalize inbound, send outbound, report status).
3. Implement webhook verification in `skylink-core` with constant-time comparison.
4. Persist an authentic inbound message through the D18 store; reject a forged one with 401.
5. Document token ownership, rotation and the raw-payload retention window.
6. Positive test: a correctly signed payload creates a message row. Negative test: tampered signature, missing header and replayed body are all rejected.
7. Confirm no secret appears in logs or in the response body.
8. Stop BLOCKED if a real bot token is required for evidence; use fixtures and say so explicitly.

## Rollback
Remove the adapter and the verification module; no schema change.
