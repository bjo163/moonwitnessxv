# M38-11 — Publish REST and WS surfaces with two auth modes and a duplicate-channel guard

**EXECUTABLE LEAF, NOT VERIFIED** · Priority P0 · Difficulty D4. [Canonical task state](../../../TODO.md) · [Milestone](../../milestones/M38.md).

## Objective and grounded context
The service only matters if other apps can call it safely. ARSY sessions are opaque database tokens, not JWTs, so SKYLINK cannot validate them locally; it must validate upstream against ARSY and cache briefly. `ChannelManager.register()` currently overwrites by id with no error, which would let two providers silently shadow each other.

## Boundaries
- Paths: `apps/skylink/src/modules/*`, `apps/skylink/src/ws.ts`, `packages/skylink-store/src/repo/*`, `apps/radio/src/lib/channels.ts` (duplicate guard only).
- Two authorization modes per route: `x-skylink-key` (service) and `Authorization: Bearer` (ARSY session). No cookies, no login endpoint.
- QR payloads are never logged and never returned to unauthenticated callers.

## Work plan
1. Pin the SHA; read the channel contract, the ARSY session resolution and the control-plane routes.
2. Implement the routes listed in the contract with response schemas and the envelope used elsewhere in XV.
3. Implement upstream session validation with a short cache (≤15s) and event-driven invalidation where possible.
4. Implement `/ws` with first-frame auth and the five documented events.
5. Make a duplicate channel id a boot-time failure with a named error; add a test for it.
6. Positive evidence: authenticated send and a WS state event. Negative evidence: 401 without credentials, 401 with an expired session, and a duplicate id failing boot.
7. Verify logs contain no token, no QR and no message body at info level.
8. Stop BLOCKED if ARSY session validation cannot be reached in the test environment; do not stub it silently.

## Rollback
Revert the routes and WS module; the store and providers remain.
