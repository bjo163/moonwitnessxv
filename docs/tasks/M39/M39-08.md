# M39-08 — Implement the content-addressed `fs` driver with quota, retention and legal hold

**EXECUTABLE LEAF, NOT VERIFIED** · Priority P0 · Difficulty D4. [Canonical task state](../../../TODO.md) · [Milestone](../../milestones/M39.md).

## Objective and grounded context
The storage guarantee is "one immutable version of the bytes". That is only true if the commit is atomic and the key is derived from the content, so the driver — not the route — owns hashing, the temporary file and the rename.

## Boundaries
- Paths: `packages/echolog-core/src/driver/fs.ts`, `packages/echolog-core/src/sidecar.ts`, `apps/echolog/src/modules/objects/*`.
- `sha256` hashing lives in the package (`apps/**` may not import `node:crypto`).
- Internal keys are `sha256/<hex>` only; original filenames live in the sidecar.
- No tables, no SQL driver, no `bytea`.

## Work plan
1. Pin the SHA; read the driver interface from M39-06 and `BLUEPRINT.md` line 174.
2. Implement temporary streaming write + incremental digest, then atomic rename on commit.
3. Write the sidecar (`filename, content_type, size, digest, uploader, created_at, retention_until, legal_hold, scan, tags`) only after the object is durable.
4. Implement quota accounting, retention evaluation, legal hold and a GC that reports what it held back.
5. Positive evidence: identical bytes uploaded twice return the same key; the object is unchanged after re-upload; the sidecar matches the bytes.
6. Negative evidence: a truncated/interrupted write leaves no visible object; delete under legal hold is refused with a reason.
7. Confirm `Select-String -Pattern 'drizzle-orm|postgres'` finds nothing under `apps/echolog` and `packages/echolog-core`.
8. Stop BLOCKED if the filesystem cannot guarantee atomic rename in the target environment.

## Rollback
Remove the storage root; every object is expendable in development and the ADR records the production caveat.
