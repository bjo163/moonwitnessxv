# M39-10 — Serve a bounded S3-compatible API from ECHOLOG's own storage

**EXECUTABLE LEAF, NOT VERIFIED** · Priority P1 · Difficulty D5. [Canonical task state](../../../TODO.md) · [Milestone](../../milestones/M39.md). Scope amended by owner direction recorded in [ADR-0007 Amendment 1](../../decisions/ADR-0007-echolog-storage.md).

## Objective and grounded context
The owner now directs ECHOLOG to serve a bounded S3-compatible protocol itself and not use MinIO. This changes the earlier outbound-driver plan. The server remains backed by ECHOLOG's own filesystem volume. It is not full AWS S3 and must not be presented as such.

## Boundaries
- Paths: `apps/echolog/src/modules/s3/*`, `apps/echolog/src/config.ts`, `packages/echolog-core/src/*`, and tests under `apps/echolog/test/*`; remove obsolete MinIO Compose/env/test setup.
- Path-style requests to one configured bucket; SigV4 `AWS4-HMAC-SHA256` Authorization-header auth with signed payloads only.
- Allow only `HeadBucket`, single-request `PutObject`, `GetObject`, `HeadObject`, `DeleteObject`, and `ListObjectsV2`.
- Object keys are write-once: identical bytes are idempotent; replacing content returns conflict. Store bytes content-addressed with filesystem sidecars/index only; do not add SQL.
- Reject multipart, browser POST, versions, ACLs, object lock, presigned/query-string auth, streaming/chunk signatures, virtual-hosted buckets, and unknown operations explicitly.
- S3 credentials live only in ECHOLOG's environment; never in consumers, Git, database or logs.

## Work plan
1. Pin the SHA; inspect Fastify raw request/path handling and the ECHOLOG storage contract.
2. Implement strict SigV4 header-auth validation using a vetted primitive; reject unsupported payload modes, stale signatures and unknown credentials before any write.
3. Add path-style single-bucket routes and bounded XML request/response handling for the allow-listed operations.
4. Map S3 object keys to immutable content-addressed bytes using filesystem metadata; preserve REST behavior and retention/legal-hold checks.
5. Test with the AWS S3 SDK pointed at ECHOLOG itself: put, head, get, list, delete; verify bytes, metadata, idempotency and client-visible errors.
6. Negative evidence: invalid signature, wrong key, stale date, unsupported multipart, path traversal, and changed-byte overwrite all fail without a write or data leak.
7. Remove MinIO service, credentials, and tests. The ECHOLOG S3 endpoint only re-opens M04-05; it does not close that task until it is hosted off the backup machine and restore is demonstrated.
8. Record exact supported client/operations and every unsupported S3 feature; do not claim full compatibility.

## Rollback
Disable the S3 listener/routes; the ECHOLOG REST API and existing filesystem objects remain available.
