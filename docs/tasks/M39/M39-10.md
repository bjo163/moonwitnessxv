# M39-10 — Add the `s3` driver, the optional profiled MinIO service and fs↔s3 parity

**EXECUTABLE LEAF, NOT VERIFIED** · Priority P1 · Difficulty D3. [Canonical task state](../../../TODO.md) · [Milestone](../../milestones/M39.md).

## Objective and grounded context
A single driver is not an abstraction, and production durability cannot rely on one host volume. This task proves the same contract on an S3-compatible endpoint without making that endpoint a mandatory container.

## Boundaries
- Paths: `packages/echolog-core/src/driver/s3.ts`, `docker-compose.yml`, parity tests under `apps/echolog/test/*`.
- Any new compose service needs a `healthcheck:` at four-space indent (`compose-contract.test.ts`) and must be opt-in (profile), not part of the default stack.
- Credentials only in ECHOLOG's environment; never in the app, Git or the database.

## Work plan
1. Pin the SHA; read the driver interface and `compose-contract.test.ts`.
2. Implement the S3 driver: put with digest metadata, head, presigned GET, delete, list for GC.
3. Add the MinIO service behind a Compose profile with a healthcheck and a named volume.
4. Write parity tests that run the same operation set against both drivers.
5. Positive evidence: upload/meta/download/delete pass identically on `fs` and `s3`; `docker compose --profile` stack reports healthy.
6. Negative evidence: with wrong credentials the driver fails closed with a clear error and stores nothing.
7. Record which gate is now unblocked: the owner-deferred off-host backup target, **only** if a bucket actually exists and a restore is demonstrated.
8. Stop BLOCKED if Docker is unavailable; say so instead of simulating parity.

## Rollback
Stop the profiled service; the `fs` driver continues to work and no object is lost.
